# 脚本设定指南

使用 [参考启动脚本.sh](参考启动脚本.sh)。本脚本保留153已跑通的单卡CPU MoE配置，默认 **BS1、DSpark7、CPU计算开启、下一层预取关闭**；可切换DSpark和预取。已对照153实际 `run.sh` 核对全部CPU/offload配置，计算与调度数值一致。路径改为环境变量，并增加启动前检查和配置记录。

## 1. 准备配套版本

**Ascend代码和CPU计算后端缺一不可**：

| 组件 | 本次配套版本 |
| --- | --- |
| vLLM | **0.30.0**，实装 `0.30.0+empty`，使用同一实验构建。 |
| Ascend | [CPU分支](https://github.com/yxk-fdu/vllm-ascend/tree/moe_cpu_compute_v1-on-0928)，固定提交 [7cf63ca](https://github.com/yxk-fdu/vllm-ascend/commit/7cf63ca477bf6045ad5a262ff6d59b66ace463bd)。 |
| CPU后端 | 完整下载 [cpu_moe/](../cpu_moe/)，对应标签 [cpu-moe-153-20261109](https://github.com/yxk-fdu/cpu_moe_compute/tree/cpu-moe-153-20261109/cpu_moe)。 |
| 环境 | Torch `2.10.0+cpu`、Torch NPU `2.10.0.post4`、CANN 9.2.0。 |

153已完成整模型启动、推理和性能测试，覆盖单卡BS1，DSpark关/7 × 预取关/开。权重需要另行准备，见 [权重准备指南](权重准备指南.md)。

在已有配套容器中安装Ascend源码，不升级vLLM/Torch：

```bash
cd "$ASCEND_REPO"
python -m pip install -e . --no-build-isolation --no-deps
python -m pip install -e ./csrc/lrc_policy --no-build-isolation --no-deps
(cd csrc/lrc_policy && python setup_npu_wait.py build_ext --inplace)
```

已有153的 `kt-native-profile-package` 时直接复用；要从CPU源码编译，在已配置CANN及构建依赖的容器中执行：

```bash
# 从CPU源码所在目录执行。构建目录必须是尚不存在的新目录。
bash cpu_moe/dependencies/ktransformers-AK/kt-kernel/build_ascend_cpu_moe.sh /workspace/kt-build-153
export KT_BUILD=/workspace/kt-build-153/package
```

`KT_BUILD` 是包含 `kt_kernel/` 的Python运行包目录，不能填CMake目录。后端应具备 `libkt_ready_poll.so`，并导出 `native_dispatch_api`、`native_cpu_handle`、`set_lifecycle_enabled`、`lifecycle_enabled`。当前源码已集成接口，无需额外补丁。编译需CMake、pkg-config/hwloc、pybind11及配套Torch环境；依赖源码相对位置保持不变。

## 2. 填写路径并启动

下面在容器内执行，路径替换为已有目录。`ASCEND_REPO` 指向前述固定Ascend源码，模型和GGUF必须对应同一模型、层号与专家编号。

```bash
export WORKSPACE=/workspace
export ASCEND_REPO="$WORKSPACE/vllm-ascend"
export KT_BUILD="$WORKSPACE/cpu_moe/kt-native-profile-package"
export MODEL_PATH=/models/DeepSeek-V4-Flash-0731
export GGUF_PATH='/models/gguf/dsv4_layer{layer_idx}_mxfp4.gguf'
export LOG_ROOT=/workspace/logs/cpu_moe

# 从本指南所在目录执行；此步只检查依赖和配置，不加载模型。
CPU_MOE_CHECK_ONLY=1 bash 参考启动脚本.sh

# 每次只启动一种配置，切换前停止上一服务。
BS=1 DSPARK=7 PREFETCH=0 bash 参考启动脚本.sh
# 其他选择：DSPARK=0关闭DSpark；PREFETCH=1开启下一层预取。
```

`WORKSPACE` 提供默认工作目录；`ASCEND_REPO` 与 `KT_BUILD` 可单独指定。`MODEL_PATH` 是NPU模型目录，`GGUF_PATH` 是CPU逐层文件模板，必须保留 `{layer_idx}`。`LOG_ROOT` 用于本次运行的日志、配置快照和profile输出，每次创建独立子目录。

脚本前台运行，Ctrl+C正常退出。切换配置时确认API与EngineCore都已退出。启动后查看 `server.log`、`additional_config.json`、`launch-config.json`，核对实际配置。

## 3. 需要按机器调整的参数

这些环境变量可直接写在启动命令前。153的编号是已验证取值，换机器或卡时先查拓扑，不能直接照抄。

| 环境变量 | 153取值 | 设置说明 |
| --- | --- | --- |
| `NPU` / `PORT` | `4` / `8144` | 使用空闲物理卡和空闲端口；物理卡4在进程内映射为逻辑卡0。 |
| `BS` | `1` | `max_num_seqs`；性能测试的请求并发必须与它一致。 |
| `DSPARK` | `0`或`7`，默认7 | 0不传推测配置；7表示DSpark草拟7个token，一个step最多8个token。 |
| `PREFETCH` | `0`或`1`，默认0 | 开关下一层预取；开启后上限固定为1个专家。 |
| `NUMA_NODE` / `CPU_THREADS` | `1` / `30` | GGUF与计算线程使用同一NUMA；153计算核32–61，线程池数1，`KT_MOE_CORE_OFFSET=0`是节点内核心序号。 |
| `POLL_CPU` / `COMPLETION_CPU` / `DMA_CPU` | `62` / `63` / `127` | 信号监测、计算完成、DMA提交分别绑核，避开计算工作核；63和127是SMT兄弟核。 |
| `HOST_WEIGHT_NUMA_NODE` | `0` | NPU搬运源的锁页权重缓冲所在节点，与CPU GGUF内存区别对待。 |
| `CPU_MOE_PROFILE` | 默认1 | 设置CPU事件输出路径，详细原生事件由profiler采集窗口开关控制；0不输出这份CPU trace。 |

启动前用 `npu-smi info`、`lscpu -e=CPU,NODE,CORE,SOCKET`、`numactl --hardware` 核对卡、核、容器允许集合及节点空闲内存。计算核、监测核与DMA核要在允许集合内，且没有明显争用。

脚本使用 `numactl --cpunodebind` 和 `--preferred`；内存首选节点允许回退，启动后可用 `numastat -p <EngineCore PID>` 和 `/proc/<PID>/task/<TID>/status` 检查实际内存与线程落点。不能仅凭节点配置值认定绑定已生效。

## 4. 保留在脚本里的关键配置

以下为153实验值，修改时编辑脚本内相应配置，不要以为它们都能通过环境变量覆盖。

| 配置 | 本次取值及含义 |
| --- | --- |
| `enabled` / `backend` / `native_dispatch` | CPU计算开启、`kt_kernel`、原生派发开启；共享信号由C++监测，直接提交CPUInfer。实际DMA仍由独立Python/Torch线程提交。 |
| `enable_cpu_binding` | **false**，避免上层绑核覆盖kt后端安排。CPU后端本身仍绑核。 |
| `transfer_policy` / `transfer_scheduler` | `load_balance` / `cpu`，按实际expert-token工作量和传输成本分配；LRC选择淘汰对象，优先搬被选择次数多的专家。 |
| CPU成本 | **93.16 μs / expert-token，约90 μs**；同一专家处理两个token计两份CPU计算，`balance_cpu_extra_route_us`也为93.16。 |
| 搬运与NPU成本 | `balance_copy_us=275.828`，按专家；`balance_npu_fixed_us=200`，按层一次。`balance_npu_route_us=2.0`，当前固定成本模型以层固定估计为主。 |
| 调度边界 | `balance_max_transfers=32`，`balance_min_gain_us=20`；时间估计的单位均为微秒，换硬件后重新校准。 |
| `num_device_experts` / `num_device_layers` | `[84]` / `2`，决定NPU驻留与显存需求，不是每次路由专家数。 |
| `max_num_tokens` | CPU后端容量48；至少覆盖 `BS × (DSPARK+1)`，增大并发需同时核对图捕获和后端容量。 |
| `KT_MOE_PIN_WEIGHTS` | **1**，开启当前搬运路径所用主存权重固定。 |
| 激活/权重复用 | `KT_MOE_MATCH_NPU_MXFP8=1`、`KT_MOE_MXFP4_TOKEN_REUSE=0`、`KT_GROUP_MIN_LEN=10`；保持本次CPU/NPU计算及成本校准口径。 |
| 热专家与预取 | 热专家预加载开启，使用Ascend源码内匹配的排名JSON；与下一层预取开关不同。预取最多1个，放在本层按需权重就绪后。 |
| 图与服务容量 | `FULL_DECODE_ONLY`，捕获尺寸 `[1,2,3,4,8,16,24,32,48]`；模型长度267000、batched tokens 32000、显存利用率0.90、KV为fp8。 |

以上成本是调度估计，不代表每次真实执行耗时固定。不要删掉CPU结果或预取权重的就绪同步来提高表面吞吐。

## 5. 验证、性能与profile

```bash
unset https_proxy http_proxy HTTPS_PROXY HTTP_PROXY
curl --fail --noproxy '*' http://127.0.0.1:8144/health
curl --fail --noproxy '*' http://127.0.0.1:8144/v1/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"deepseek_v4","prompt":"What is 16 minus 3 minus 4?","max_tokens":20,"temperature":0}'
```

改端口后同步修改curl。profile为delay=2、最大200步；DSpark7短采集用 `max_tokens=20`，让请求自然结束再stop。采集与合成流程见 [profile合成指南](../profile合成指南/README.md)，也可直接复制 [发给agent的合成指令](../profile合成指南/如何让agent合成profile.md)。默认只下载最终trace JSON到本地桌面。

性能测量在关闭采集时单独进行。AISBench perf模式每轮先5条成功预热，再统计20条请求；相同配置重复3次取平均，保持并发、输入集和输出上限一致。
