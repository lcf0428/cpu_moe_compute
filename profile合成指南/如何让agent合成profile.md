# 如何让agent合成profile

把下面整段发给agent，并填写服务器与本次采集目录即可。知道具体日志路径时一并填写；不知道可留空，让agent在本次采集目录内查找。

## 复制给agent的指令

```text
请参考 https://github.com/yxk-fdu/cpu_moe_compute/tree/main/profile合成指南 ，
为我合成本次CPU MoE与NPU的profile，并下载最终合成JSON。

服务器或SSH连接别名：<填写可连接的服务器或别名；本地数据则写“本地”>
本次采集目录：<填写真实路径>
CPU后端/工作区目录：<知道则填写，不知道请从运行记录查找>
原始NPU trace路径：<已知则填写，否则在本次目录查找>
CPU日志路径：<已知则填写，否则在本次目录查找>
本地下载目录：默认使用当前用户桌面下新建的 profile_<本次采集时间> 文件夹；
如果我另给绝对路径，则优先使用该路径。不要覆盖已有文件。

请直接完成以下工作：
1. 读取上述仓库的合成指南、合成脚本及参考profile说明。先核对服务使用的代码版本和实际日志格式，优先使用服务器已有且与本次日志匹配的合成器，不用旧脚本覆盖当前实现。
2. 找到同次采集、同worker PID的原始NPU trace、CPU计算日志，以及可用的时钟锚点/同步证据。不要盲选latest，不要把已有合成JSON再次当作原始trace输入。确认profiler解析已经完成，文件不再变化。
3. 使用可靠时钟映射对齐CPU和NPU。若有本次预取、DMA与原生生命周期事件，使用匹配的分析/合成逻辑一并保留；缺少专用合成器时检查实际事件字段和源码后适配，不得凭名称或截图编造时间点。缺少必要输入或可靠校时依据时，明确说明具体缺项并询问我，不要猜偏移或交付空合成。
4. 只保留本次CPU计算和匹配往返覆盖的连续时间窗口；保留窗口内原始NPU、CANN、Python、draft及Overlap Analysis等轨道和元数据。保持Stream原名与顺序，CPU实际计算轨道放在设备流上方。不要合并成简化两轨图，不删除活跃轨道，不移动事件来制造重叠。
5. 对大绝对时间戳使用Decimal等精确处理；窗口内部原事件的pid/tid、ts/dur、算子和参数保持原值，仅对跨窗口事件裁剪。专家传输T计数基于实际记录，不能把预取数量当作真实按需传输数量。
6. 检查JSON有效性、实际CPU计算区间非空、时钟映射及窗口覆盖、未匹配区间、丢弃日志计数；有缺失或校时不确定性时如实说明。不得将截图重叠等同于性能提升。
7. 只下载一个最终合成trace JSON到本地桌面的本次子目录：包含预取信息时命名 trace_view_cpu_compute_prefetch.json，否则命名 trace_view_cpu_compute.json。不要仅因文件名带prefetch就声称含有预取事件。若服务器侧临时压缩用于传输，在本地解压为该JSON，校验完成后不保留临时压缩包。
8. 不下载原始trace、CPU JSONL、其他统计JSON、报告TXT、数据库、校时文件、图片、压缩包或整个profiler目录。需要的统计/报告可保留在服务器供验证，不复制到本地。
9. 比较服务器最终JSON与本地JSON的SHA256和大小，均一致后才报告成功。最终只告诉我本地JSON路径、匹配/校时是否正常及必须说明的缺项；不要删除服务器原始输入，不要重启或停止其他人的任务。
```

## 默认交付

桌面本次任务子目录中只保留一个可直接用MindStudio打开的合成trace JSON。这里的“只下载JSON”仅指最终trace，不包括其他名称的统计JSON。参考样例见 [参考profile](参考profile/README.md)。
